When an MCP result loses its error flag

22 November 2026

A tool call can fail while its wrapper reports success. In rigout, one cause was a result without a recognised error flag.

rigout gives authorised AI agents access to a machine through MCP. It supports command execution, files and Docker. A false success result can send the next step in the wrong direction.

The defect was in the result adapter. MCP used isError in one supported version and is_error in another. The adapter checked both names. If neither existed, its fallback returned None. Python converts None to False. The wrapper therefore treated an unknown result as a successful call.

The merged repair gives an absent field its own value. The adapter reads either known field. If both fields are absent, it raises UnknownResultShapeError and includes a preview of the result.

A field that exists with a value of None remains distinct from an absent field. This preserves the supported result behaviour while rejecting an unknown format.

The implementation and regression tests show the exact cases. The tests cover both field names, true and false values, an explicit None, and an object with neither field.

For a tool adapter, the useful question is simple: what happens when the response changes shape? Test that case directly. A familiar success response cannot prove how an unfamiliar response will behave.

This repair is merged in the repository. It does not establish that every installed package contains the repair.
